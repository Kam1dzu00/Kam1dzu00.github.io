ЗАДАЧА

Соединить полевые данные, учёт и маркировку без ручной склейки

Данные появлялись в мобильном приложении, JSON-файлах, XML-документах, регистрах 1С и внешних сервисах. Для контроля требовалось не просто загрузить коды, а восстановить агента, торговую точку, склад и маршрут, проверить упаковочную иерархию, сохранить ошибки и дать руководителю понятный результат.

ТРИ СВЯЗАННЫЕ ПОДСИСТЕМЫ

Глубина проекта раскрывается по слоям

Каждая глава решает самостоятельную задачу, но ценность появляется именно в их совместной работе.

01

Полевые сканы → JSON → два FTP → 1С

Торговые агенты передают сканы продукции и контекст продажи. 1С забирает файлы, проверяет структуру, нормализует коды и восстанавливает объекты учёта.

Mobile scan→JSON→FTP × 2→Validation→Register
  • Раздельная обработка каждого файла
  • Маршрутизация успешных и ошибочных результатов
  • Статистика: всего, добавлено, дубли, ошибки
  • Fallback-поиск агента и маршрута
02

Честный ЗНАК → True API → документ и упаковка

Список документов не содержит всей бизнес-информации. Система получает кандидатов через doc/list, читает полный JSON через doc/info и только после этого применяет фильтры и проверяет коды.

Session→doc/list→doc/info→Business filters→Pack tree
  • Пагинация и несколько стратегий запроса
  • Одна контролируемая попытка обновления сессии
  • Фильтрация по типу, статусу, дате и причине
  • Иерархия пачка → блок → короб
03

XML / TXT → коды → регистр → сверка

Отдельный входной контур читает пакет документов, извлекает атрибуты и коды упаковок, исключает уже обработанные значения и сохраняет статистику по каждому файлу.

Folder→XML/TXT→Attributes→Deduplication→Analytics
  • Потоковое чтение XML без загрузки всего файла в память
  • Поддержка нескольких узлов с кодами
  • Проверка дублей до записи
  • Ошибки одного файла не останавливают пакет

ENGINEERING DECISIONS

Почему система устроена именно так

Здесь важнее не синтаксис BSL, а решения, которые делают production-процесс повторяемым, диагностируемым и безопасным.

01

Work / Done / Error

Состояние файла выражено каталогом.

Оператор видит результат без открытия 1С, а повторный запуск не смешивает новые и уже обработанные данные.

02

Нормализация до сравнения

DataMatrix приводится к каноническому виду один раз.

Все последующие проверки работают с единым форматом и не размножают ветвления по длинам и служебным символам.

03

Несколько стратегий агента

Точное совпадение дополняется нормализацией пробелов и Е/Ё, затем fallback по складу.

Production-данные заполнены неидеально, но неоднозначность должна оставаться заметной и диагностируемой.

04

doc/list → doc/info

Сначала дешёвый список кандидатов, затем полный документ.

True API не возвращает причину операции в списке, поэтому корректный бизнес-фильтр возможен только по полному JSON.

05

Ошибка файла изолирована

Каждый входной файл обрабатывается в собственной защищённой секции.

Один повреждённый JSON или XML не должен блокировать весь пакет и скрывать успешно обработанные данные.

06

Регистр как аналитический слой

Отчёты читают подготовленные записи, а не исходные файлы.

Источник можно менять независимо от СКД, а сверку можно повторять и объяснять пользователю.

07

Временные таблицы

Нормализованные агенты, маршруты и данные собираются по этапам.

Сложный запрос становится проверяемым, повторные вычисления сокращаются, fallback-логика остаётся явной.

08

Один контролируемый retry

При 401/403 сессия обновляется и запрос повторяется один раз.

Это восстанавливает ожидаемое истечение сессии, но не создаёт бесконечный цикл при системной ошибке.

09

Неизвестное не равно успеху

Пустой или неожиданный ответ фиксируется как отдельный исход.

В маркировке ложноположительный результат опаснее честного сигнала о неопределённости.

10

Журналирование как часть архитектуры

Тип, источник, файл и контекст ошибки сохраняются структурированно.

Поддержка может воспроизвести сбой и исправить данные без поиска по сообщениям пользователя.

PRODUCTION LESSONS

Что реальная эксплуатация изменила в подходе

Эти выводы появились не из учебника, а после поддержки обменов, внешних API и пользовательских сценариев в рабочем контуре.

01

Повторный запуск проектируется заранее

Пакетный процесс должен отличать новые, завершённые и ошибочные данные, иначе восстановление после сбоя само создаёт дубли.

02

Наблюдаемость важнее сообщения «готово»

Количество входных, добавленных, повторных и ошибочных записей нужно возвращать пользователю и сохранять в журнале одним контрактом.

03

Неидеальные данные — нормальное состояние production

Fallback помогает продолжить работу, но неоднозначность нельзя скрывать: она должна оставаться видимой для проверки и исправления.

04

Интеграция заканчивается бизнес-результатом

Получить JSON недостаточно. Ценность появляется после восстановления документа, агента, маршрута и понятного отчёта для пользователя.

ОБЕЗЛИЧЕННЫЙ PRODUCTION-КОД

Семь фрагментов, семь инженерных компетенций

Фрагменты сокращены и очищены от реквизитов, адресов и внутренних имён. Логика соответствует реальному решению; это витрина подходов, а не публикация полного модуля.

01 / PIPELINE

Маршрутизация файлов по результату

Два входных FTP обрабатываются одинаковым конвейером, а сбой конкретного файла не останавливает очередь.

WHY

Состояние данных наблюдаемо снаружи, повторная обработка контролируема, а ошибка сохраняет имя источника и файла.

1C / BSLFTP.bsl
Процедура ОбработатьОчередьFTP(НомерИсточника)
    Соединение = ПодключитьсяКFTP(НомерИсточника);
    Файлы = Соединение.НайтиФайлы("/work", "*.json");

    Для Каждого Файл Из Файлы Цикл
        Попытка
            ЛокальныйФайл = СкачатьВоВременныйКаталог(Файл);
            Результат = ОбработатьJSONФайл(ЛокальныйФайл);

            КаталогНазначения = ?(
                Результат.Успех,
                "/done/",
                "/error/");

            Соединение.Переместить(
                Файл.ПолноеИмя,
                КаталогНазначения + Файл.Имя);
        Исключение
            ЗаписатьОшибкуОбмена(
                НомерИсточника,
                Файл.Имя,
                ОписаниеОшибки());
        КонецПопытки;
    КонецЦикла;
КонецПроцедуры
02 / CONTRACT

Структурированный результат загрузки

Каждый JSON возвращает не только флаг успеха, но и измеримый итог обработки.

WHY

Пользователь и журнал получают одинаковую картину: сколько кодов пришло, добавлено, отброшено как дубль и завершилось ошибкой.

1C / BSLJSON.bsl
Результат = Новый Структура;
Результат.Вставить("Успех", Ложь);
Результат.Вставить("ВсегоКодов", 0);
Результат.Вставить("Добавлено", 0);
Результат.Вставить("Дубли", 0);
Результат.Вставить("Ошибки", 0);
Результат.Вставить("ТекстОшибки", "");

Чтение = Новый ЧтениеJSON;
Чтение.ОткрытьФайл(ПутьКФайлу);
Данные = ПрочитатьJSON(Чтение, Ложь);
Чтение.Закрыть();

Результат.ВсегоКодов =
    Данные.TT_INFO.DataMatrix.Количество();
03 / NORMALIZATION

Каноническое представление DataMatrix

Входные системы передают служебные символы и несколько представлений GS1.

WHY

Нормализация на границе системы уменьшает сложность поиска дублей, сопоставления и внешних запросов.

1C / BSLDM.bsl
Функция НормализоватьDataMatrix(ИсходныйКод)
    Код = СокрЛП(Строка(ИсходныйКод));
    Код = СтрЗаменить(Код, Символы.ПС, "");
    Код = СтрЗаменить(Код, Символы.ВК, "");
    Код = СтрЗаменить(Код, Символ(29), "");

    Если СтрДлина(Код) = 41
        Или СтрДлина(Код) = 31 Тогда
        Возврат Лев(Код, 25);
    КонецЕсли;

    Если ЭтоGS1СоСкобками(Код) Тогда
        Возврат СобратьКаноническийКодGS1(Код);
    КонецЕсли;

    Возврат Код;
КонецФункции
04 / TRUE API

Двухэтапное чтение документов

Причина операции доступна только в полном теле документа.

WHY

Список используется как быстрый предварительный фильтр, а дорогое чтение деталей выполняется только для кандидатов.

1C / BSLAPI.bsl
// True API не возвращает причину в doc/list.
// Поэтому сначала получаем страницу документов,
// затем читаем полный JSON каждого кандидата.

Список = ПолучитьСписокДокументов(
    Параметры,
    ТочкаПагинации,
    КлючСессии);

Для Каждого Документ Из Список.Документы Цикл
    Если Не ПодходитПоБыстрымФильтрам(Документ) Тогда
        Продолжить;
    КонецЕсли;

    Детали = ПолучитьДокументJSON(
        Документ.DocId,
        КлючСессии);

    Если ПодходитПоПричине(Детали.JSON, Причина) Тогда
        СохранитьРезультат(Документ, Детали.JSON);
    КонецЕсли;
КонецЦикла;
05 / RESILIENCE

Ограниченное восстановление сессии

Сессия внешнего сервиса может истечь во время длинного пакетного процесса.

WHY

Одна повторная попытка закрывает ожидаемый сценарий истечения токена и не маскирует постоянную ошибку.

1C / BSLAUTH.bsl
Для НомерПопытки = 1 По 2 Цикл
    Ответ = ВыполнитьGET(
        URLДокумента,
        КлючСессии);

    Если Ответ.КодСостояния = 401
        Или Ответ.КодСостояния = 403 Тогда

        Если НомерПопытки = 1 Тогда
            КлючСессии =
                ОбновитьКлючСессии(Организация);
            Продолжить;
        КонецЕсли;

        Возврат ОшибкаАвторизации(Ответ);
    КонецЕсли;

    Прервать;
КонецЦикла;
06 / BATCH INPUT

Потоковый разбор XML

Документы обрабатываются пакетно, а коды могут встречаться в разных узлах формата.

WHY

Потоковый парсер экономит память и позволяет фиксировать результат каждого файла независимо.

1C / BSLXML.bsl
Парсер = Новый ЧтениеXML;
Парсер.ОткрытьФайл(ИмяФайла);

Пока Парсер.Прочитать() Цикл
    Если Парсер.ТипУзла = ТипУзлаXML.НачалоЭлемента
        И Парсер.Имя = "Файл" Тогда
        Идентификатор = Парсер.ЗначениеАтрибута("ИдФайл");
    ИначеЕсли Парсер.ТипУзла = ТипУзлаXML.НачалоЭлемента
        И (Парсер.Имя = "НомУпак"
            Или Парсер.Имя = "КИЗ") Тогда
        ДобавитьКодЕслиНовый(
            Парсер.ПрочитатьСодержимоеКакСтроку(),
            Идентификатор);
    КонецЕсли;
КонецЦикла;

Парсер.Закрыть();
07 / DCS / QUERY

Восстановление маршрута с fallback

Маршрут определяется на дату продажи сначала по агенту, затем по складу.

WHY

Приоритет бизнес-правил виден прямо в запросе, а временные таблицы разделяют нормализацию и финальную аналитику.

1C / BSLQUERY.bsl
ВЫБРАТЬ
    Данные.ДатаПродажи,
    Данные.Агент,
    Данные.Склад,
    Данные.ТорговаяТочка,
    ВЫБОР
        КОГДА МаршрутАгента.Номер ЕСТЬ НЕ NULL
            ТОГДА МаршрутАгента.Номер
        ИНАЧЕ МаршрутСклада.Номер
    КОНЕЦ КАК НомерМаршрута
ПОМЕСТИТЬ ВТ_ДанныеСМаршрутом
ИЗ
    ВТ_Данные КАК Данные
    ЛЕВОЕ СОЕДИНЕНИЕ ВТ_Маршруты КАК МаршрутАгента
    ПО Данные.Агент = МаршрутАгента.Агент
       И Данные.ДатаПродажи МЕЖДУ
          МаршрутАгента.ДатаНачала
          И МаршрутАгента.ДатаОкончания
    ЛЕВОЕ СОЕДИНЕНИЕ ВТ_Маршруты КАК МаршрутСклада
    ПО Данные.Склад = МаршрутСклада.Склад;

РЕЗУЛЬТАТ

Не просто автоматизация файла, а управляемый производственный контур

Решение соединяет сбор данных, интеграции, предметную логику и аналитику. Его можно сопровождать, повторно запускать, диагностировать и расширять без ручной сверки каждого промежуточного шага.

Обсудить похожую задачу
  • Многодневные ручные проверки заменены повторяемыми запусками
  • Ошибки и дубли не теряются и не маскируются
  • Руководитель видит расхождение в бизнес-контексте
  • Внешние сервисы и входные файлы отделены от аналитического слоя

Интерфейсы и код показаны в обезличенном виде. Секреты, адреса, внутренние пути и данные организаций не публикуются.
